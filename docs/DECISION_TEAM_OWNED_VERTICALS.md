# Decision Record — Team-Owned Verticals: "One Team, One Project, One Image"

**Date:** 2026-10-18
**Status:** Decided — **Phases 0–7 implemented & verified** (Go present via `devenv.nix`)
**Decision owner:** architecture review
**Supersedes:** the *source-ownership split* implied by the `modules/` + `pages/`
dichotomy in [`ARCHITECTURE.md`](../ARCHITECTURE.md) §1 and the cross-team
boundary-rule spread across `internal/architecture`. It **preserves** the
ownership *semantics* — who owns UI, who owns the domain, who owns deployment —
and re-homes them so each is held in **one place**.
**Scope note:** a *containment* refactor. It moves where ownership lives, not
what is owned. Domain still lives in Go; the gateway still serves one binary
today; the cross-team UI contract (D-021) still stands — it is now declared by
the vertical that owns it.

## 0. Why this record exists

The governance for Gogo is correct but **scattered**. A single feature team's
bounded context leaves fingerprints in at least six places, each with its own
file, its own rule, its own test:

| Concern | Today's scattered homes | What a team must touch |
| --- | --- | --- |
| Backend behaviour | `internal/modules/<f>/{domain,application,infrastructure,presentation}` | hexagonal package tree |
| The page that renders it | `internal/pages/<page>/{handlers,views,application,infrastructure}` | a *different* tree, with import rules tying them |
| Shared UI primitives | `design-system/web/ui/*.templ` | a third tree (correctly shared) |
| Cross-team UI grant | `docs/ADR_CROSS_TEAM_UI_CONTRACT.md`, `internal/architecture/ui_contract_test.go` | a fourth place |
| Composition | `internal/bootstrap/di.go` (mounts modules *and* pages) | a fifth place |
| Boundary enforcement | `internal/architecture/architecture_test.go`, `layers_test.go`, `ui_contract_test.go`, `TestImportGraphIsCurrent`, `import_graph.txt` | a sixth place, plus a graph snapshot |

That is not a scalability problem — 7 modules, 4 pages, one team
([`DECISION_UI_OWNERSHIP.md`](./DECISION_UI_OWNERSHIP.md) §1.4 says slot
composition is not worth it at this scale). It is a **cognitive-load and
ownership problem**: to understand a feature, or to change the ownership of one,
you have to read six files across three trees and reason about five rules.

This record adopts the model Gogo's own evidence already points to. The
single most robust frontend-ownership pattern in production is the **self-
contained vertical** — the pattern Keycloak exemplifies: **one deployable image
ships both the UI and the backend of a vertical** (the Keycloak admin console +
the IAM service are one JAR, one container, one team). The team owns the whole
thing, end to end. Nothing is "someone else's page" or "someone else's rule".

The rule this record imposes is not a new abstraction — it is the opposite. It
**removes** the abstract separation (page/module) that created the scattered
homes, and substitutes a physical one: **a team's code lives under one
directory**. Boundary enforcement then comes from the directory/package
boundary itself, not from a distributed set of import-rule tests.

## 1. The model

```
internal/
  features/<feature>/
    OWNERS.md          # who owns this vertical; the single ownership source
    README.md          # the vertical, in one page
    domain/            # aggregates, value objects, invariants (unchanged, moved)
    application/       # use cases + ports (in) / ports (out)
    infrastructure/    # persistence, remote clients, gateways
    presentation/      # gRPC surface (the module's remote contract is *here*)
    routes.go          # HTTP route ownership — the vertical owns its routes
    ui/                # this feature's page(s) + Templ components (the "page")
    public/            # the ONLY cross-team UI surface a vertical may import (D-021)
    events.go          # publishes / subscribes on the shared bus (its vocabulary)
    compose/           # builds its own graph (its DI), instead of bootstrap
    *_test.go          # unit + boundary + one vertical integration test

  shell/               # the composition root (renamed from internal/bootstrap)
    shell.go           # startup steps: signal handling, BuildGateway
    di.go              # the object graph: config, bus, registry, ports, connections
    units.go           # the unit table: which verticals are mounted, and how
    module_gateway.go  # HTTP server, health, readiness — NOT page composition
    *_connection.go    # product-platform dials + the in-process vertical mounts
```

What used to be "a module" and "a page" for the same feature is now **one
vertical**. The feature team's entry point is `internal/features/sales/`; there
is nowhere else to look.

### 1.1 The four answers

| Question | Old answer (scattered) | New answer (contained) |
| --- | --- | --- |
| **Where is the feature's backend?** | `modules/<f>` | `features/<f>/{domain,application,infrastructure,presentation}` |
| **Where is the feature's UI?** | `pages/<owner>` under a separate tree | `features/<f>/ui` — same directory as its backend |
| **Who decides what's on a page?** | the page-owning team, via import rules | the vertical that owns the route — a route has one owner, and that owner is the vertical |
| **Who can show another team's UI?** | a page, importing `<module>/public` | a vertical, importing `<feature>/public` — the same grant, re-homed |
| **Where do cross-team rules live?** | 3 test files + a graph snapshot | 1 boundary test + the `internal/` compiler rule + the package contact surface |

## 2. What is preserved, verbatim

This record does **not** change the ownership semantics this codebase
already decided. It re-homes them.

### 2.1 UI ownership team topologies — preserved

- **A route has one owning team** (DECISION_UI_OWNERSHIP §2). That owning team
  is now the vertical, and its routes live in `features/<f>/routes.go`. A route
  is co-located with the code it renders — you cannot own half a route.
- **The owning team decides what appears on its page** (§3). Import rules are no
  longer the mechanism; the directory is. The page and its arrangement are the
  same package, so there is no composition decision to delegate.
- **A team may contribute its feature to another team's page only through its
  declared `public` surface** (D-021 / ADR_CROSS_TEAM_UI_CONTRACT §4.1). That
  surface now lives *inside* the vertical as `features/<f>/public`. The grant is
  unchanged: pages may import `<feature>/public`; internals stay closed; a page
  never imports another page. It is just declared in the owning team's directory
  instead of a hypothetical sibling.
- **Slot composition, widget layers, island registry, runtime-distributed
  components are still explicitly not built** (DECISION_UI_OWNERSHIP §2
  "Explicitly not built"). Consolidation does not add a composition engine. The
  break-even evidence (§1.4) still stands; Gogo is not at 15+ teams.

### 2.2 Domain ownership — preserved

- The **platform owns the product aggregate** ([D-018](../ARCHITECTURE.md#d-018)).
  Verticalisation touches no domain. `features/storefront/ui` (a page context)
  still reads product through the vendored contracts via `productconsumer`, and
  rule 6 (only `productconsumer` imports the product contracts) is unchanged.
- `features/inventory` still owns stock; `features/sales` still *composes*
  `inventory.v1.AdjustStock` ([D-015](../ARCHITECTURE.md#d-015)); the auth module
  still owns the merchant relationship ([D-022](../ARCHITECTURE.md#d-022)). The
  vertical directory is a re-homing, not a re-architecture of the domain.
- Re-homing never creates a second authority: a vertical's `ui` reads through the
  same remote contracts and `application` ports it always did. Moving the file
  does not move the seam.

### 2.3 Deployment ownership — preserved, and made explicit

- The gateway still ships **one binary** today
  ([ADR_CROSS_TEAM_UI_CONTRACT](./ADR_CROSS_TEAM_UI_CONTRACT.md) §2.2). A vertical
  is an **in-process** unit inside that binary, the same way the monolith works
  now. This is the Keycloak model *within a monolith*: one image, several
  self-contained verticals, each a team's whole product.
- A vertical is the **lift-out seam**. Because each vertical already publishes a
  remote contract (D-001), promoting a vertical to its own service is a
  deployment change, not a redesign: `features/<f>` becomes `services/<f>`, its
  `compose` is already its root, and the gateway's in-process dial is replaced by
  a network dial (the `*_connection.go` files in shell already encode that swap).
- **One image per vertical is the destination, not a promise.** Today one binary
  = one image. The trigger to physically split a vertical is the same as D-018's
  exit condition: a second authority for one row, or an independent release
  cadence. Until then the consolidation is about *source containment*, not
  process topology — precisely so that when a split happens, no ownership has to
  be re-decided.

### 2.4 Multi-client UI — preserved

`templ.Component` remains the web composition unit (ADR_CROSS_TEAM_UI_CONTRACT
§2.1, §4.1); the design system stays `design-system/` (platform-owned). Mobile
and desktop own native implementations; they are never asked to embed web
components. Verticalisation is a web-runtime re-home; it touches nothing native.

## 3. The single boundary mechanism (the answer to "boundaries scattered")

The complaint is not that boundaries are too strict — it is that a boundary is
enforced by **many mechanisms in many places**, and ownership is split so a team
must thread many seams. The consolidation collapses them:

| Category | Old mechanism (many) | New mechanism (one) |
| --- | --- | --- |
| A team's code is reachable | 6 layout rules across the tree | **one directory** (`features/<f>`) |
| A team can't touch another team's internals | `TestImportBoundaries` + `TestCompositionLayerReachesNoModuleInternals` + the `public` grant fixture | the **`internal/` compiler rule** + the **`public/` contact surface** declared in-vertical |
| A team can't re-implement another's domain | import rules 6 & 7 (product/catalog) + architecture tests | unchanged, but now co-located with the rule's owner |
| Which team owns what | the graph snapshot + PROSE in README/ADRs | **`OWNERS.md` at `features/<f>/`** (one file per vertical) + `CODEOWNERS` at repo root |
| Cross-team UI visibility | 3 architecture tests + synthetic fixtures | **`features/<f>/public`** as a package export; `internal/` compiler rule; one boundary test |

A vertical is a **closed module** to every other vertical *by construction*
(Golang's `internal/` path visibility), except for its declared `public`
package. That is the same guarantee the current tests simulate, but it is now a
property of the file system, not a regression test. The boundary lives where the
code lives, so it cannot rot.

## 4. The migration program (phased, low-risk)

A physical re-home of ~40 packages must be incremental and stay green at every
step, with Go present. Do **not** move packages in one patch; no CI safety net
exists and the import graph is a snapshot that must be regenerated. The ordering
below is by risk, lowest first.

### Phase 0 — Baseline & tooling (do first) ✅ done
- Install the FOUNDATION for the re-home: a `make feature` target and the
  `scripts/feature-vertical.sh` scaffolder (this repo).
- Add the `OWNERS.md` + `CODEOWNERS` mapping for the current tree so the target
  ownership is declared before any move.

### Phase 1 — Re-home the design-system dependency (no logic change) ✅ done
- `design-system/web/ui` is already a standalone module (rule 5). Leave it. It is
  the one thing that *should* stay shared. Confirm nothing else owns primitives.

### Phase 2 — Smallest vertical first: `ops` ✅ done
- `ops` is a probe/health context with no page consumer. Move
  `internal/modules/ops` → `internal/features/ops` as a *vertical* first. Its
  `routes.go` is empty (no page), its `ui` is empty. This proves the layout and
  the scaffold without touching composition or contracts.

### Phase 3 — Feature + page the same team owns: `sales`/`seller` ✅ done
- `internal/modules/sales` and `internal/pages/seller` are the strongest
  "one team, one vertical" pair (the seller console composes sales + inventory).
  Merge the seller page's read-side into `features/sales`, with the read-side
  kept under `ui/` to avoid the `application`/`infrastructure` name clash with
  the backend hexagon: backend at the feature root
  (`domain/application/infrastructure/presentation/compose`), read-side at
  `ui/{application,infrastructure,handlers,httperr,views}` plus `ui/page.go`.
  The page's route moved with it (`ui.RegisterRoutes`); the `sales.v1` gRPC
  surface stays in `features/sales/presentation`.
- **Done & verified (2026-10-19):** both re-homed, `OWNERS.md` written, and the
  boundary + layer-matrix guarded by `vertical_boundary_test.go`. The read-side
  is decoupled from the backend domain: it talks to `sales`/`inventory` over
  `gogo/contracts/*` + `internal/shared`, never the backend hexagon.

### Phase 4 — Auth tenant/identity vertical: `auth` ✅ done
- Merge `modules/auth` + `pages/auth` into `features/auth`. Its `public` package
  is the natural first real consumer of the D-021 grant (a login/account widget
  a storefront can embed) — extract it only if a genuine consumer appears, per
  the existing rule.
- **Done & verified (2026-10-19):** merged into `internal/features/auth` (backend
  hexagon at the root, login page under `ui/`, `OWNERS.md`). No `public` was
  extracted — no consumer exists. Merging also surfaced the DI key defect
  recorded in the status section (`typeKey` now keys by import path).

### Phase 5 — Remaining pages that are owners, not consumers: `home`, `profile`, `contentcms` ✅ done
- `home` and `profile` became **read-side verticals**. A vertical owns a `ui/`
  that composes other verticals' `public` surfaces (D-021) but never their
  internals. `contentcms` was already a read-side context; re-homed as
  `features/contentcms`.
- `inventory`, `billing` were module-only (no page) → re-homed to
  `features/{inventory,billing}`; `billing` owns the activity-feed UI inside its
  flat package.
- **Done & verified (2026-10-19):** `pages/{home,profile,contentcms}` →
  `features/*/ui`; `modules/{inventory,billing}` → `features/*`; `OWNERS.md`
  each. `contentcms` carries no `Register` (the shell provides its `Reader` and
  `PageHandler` directly, so it is deliberately absent from the unit table).

### Phase 6 — Retire the empty shell & old seams ✅ done
- Deleted `internal/pages/` once every page was re-homed.
- `internal/bootstrap` is `internal/shell` (composition root only: config, bus,
  registry, gateway, health; the shell lists the verticals and provides their
  ports — each vertical owns its routes and its own `compose`).
- The four `*_connection.go` files stay (they encode the in-process↔network dial
  swap that makes lift-out a config change).
- The retired module scaffolder (`cmd/modulegen` + `make module`) was deleted
  with the root it generated into; `make feature` is the one entry point.

### Phase 7 — Enforce, then regress ✅ done
- Enabled the single-boundary test (§5), deleted the superseded architecture
  tests (`TestHexagonDependencyDirection`, the module/pages predicates and the
  `ui_contract_test.go` fixtures), retargeted
  `TestCompositionLayerReachesNoVerticalInternals`, added
  `TestRetiredRootsStayRetired`, regenerated `import_graph.txt`, ran
  `go vet ./...` + `go test ./... -race`, and left the graph as the new
  baseline.

The net effect after Phase 6: a feature is one directory; ownership is one file
per vertical; the boundary is one mechanism; the composition is one place (the
shell) and never scattered into pages.

## 5. Enforcement spec (implemented)

The three cross-team tests are replaced by one boundary test that reads the import
graph and asserts the single ownership rule. It is **already written and green** in
this repo:

```go
// internal/architecture/vertical_boundary_test.go
// TestFeatureVerticalIsAClosedModule asserts the single ownership rule: a
// package inside internal/features/<f> may import only its own subtree,
// internal/shared, or gogo/contracts — never another vertical's internals, and
// never a module or page tree. Cross-vertical contact, when a real one exists,
// is the declared <feature>/public surface (D-021), added only when a consumer
// appears. This codifies "one team, one project, one image".
```

`TestFeatureVerticalHexagonDependencyDirection` in the same file keeps the
ARCHITECTURE.md layer matrix applied to feature verticals; its module-era runner
(`TestHexagonDependencyDirection`) and the module/pages predicates were deleted
in Phase 7, so every vertical is in scope and none can escape by living outside
a directory the old runner watched.

Extend this same test with the `/public` grant rule once a genuine cross-vertical
consumer exists; no additional boundary mechanisms are added elsewhere. The net
effect a team should discover is that the *only* two things governing a
vertical's borders are the `internal/` compiler rule and this one boundary test.

And the `make feature` scaffolder (this repo's `scripts/feature-vertical.sh`)
creates an empty vertical with an `OWNERS.md`, the standard directory set,
`routes.go` and `events.go`. Both run in the team's Go toolchain, now present via
`devenv.nix`.

## 6. What is deliberately ruled out, and the trigger to revisit

| Ruled out | Trigger to revisit |
| --- | --- |
| Splitting features into separate processes/services now | A second authority for one row (D-018's condition), an independent release cadence, or a hard resource isolaion requirement |
| Slot/widget composition engine (page composition is directory-ownership) | More than ~15 teams, or a page needing 3+ teams' features on a stable cadence (DECISION_UI_OWNERSHIP §1.4) |
| Moving the domain into a JS/UI layer | Never. The domain stays in Go; the platform owns product (D-018) |
| A per-team design system | A second client runtime. `design-system/` stays platform-owned (rule 5) |
